## Product design

### Goals / Non-goals

**Goals**: a first version of `netsuite-mcp` that lets an agent, acting on behalf of one NetSuite account (identified by the caller's own Token-Based Authentication credentials, forwarded per request), inspect and manage that account's ERP/CRM records through NetSuite's public SuiteTalk REST Web Services:

- Discover what record types exist in the account and what fields each one has — NetSuite's record model is account-specific (standard records plus any custom records/fields the account has configured), so discovery has to be a tool, not a hardcoded list.
- Search and report across records using SuiteQL — this is NetSuite's own recommended way to filter/join/aggregate (the plain record-list endpoint only pages through ids, it cannot filter).
- Read, create, update, and delete individual records by record type + id — covering the full ERP lifecycle (e.g. create a sales order, update a customer's credit limit, void/delete a draft transaction) that "live access" to an ERP implies, not just read access.

**Non-goals** (v1):

- **No per-record-type tools** (no `netsuite_create_customer`, `netsuite_create_sales_order`, etc.). NetSuite ships hundreds of record types, and accounts can add custom ones — a tool per type does not scale and most would sit unused. See Decisions made by DEV01, item 1.
- **Financial period/accounting-preferences configuration, subsidiary/role/employee-permission setup, tax configuration, SuiteScript/workflow deployment, CSV import/export jobs, approval-routing configuration.** These are account-administration surfaces, not day-to-day record work, and several are destructive at the tenant-configuration level in ways that deserve a dedicated review with a named business case.
- **File Cabinet (document storage), attach/detach operations, batch/bulk operations** — not named by the ticket; NetSuite's batch endpoint processes arrays of CRUD operations in one call, which is a genuine convenience but adds a second, more complex contract shape (array-of-operations with per-item results) — deferred until a concrete workflow needs it (see Reuse & cleanup → Follow-ups).
- **SuiteAnalytics Workbook / saved search execution** — a different, older NetSuite query surface with its own permission model; SuiteQL already covers ad-hoc querying for this v1.
- Any UI. This is a backend MCP connector with no end-user-facing screen; "space with empty/loading/error states" does not apply.

### Acceptance criteria AC1..AC17

- **AC1**: Given valid credential headers, When `netsuite_list_record_types` is called, Then it returns the catalog of record types available in that NetSuite account (from NetSuite's own metadata catalog).
- **AC2**: Given a record type, When `netsuite_get_record_schema` is called, Then it returns that type's field list (name, type, required/optional) from NetSuite's metadata catalog for that record type.
- **AC3**: Given a record type, When `netsuite_list_records` is called, Then it returns a paginated list of that type's record ids/links, capped at the connector's own page-size limit (§2.5 of the SOP), with `has_more`/next-offset when truncated.
- **AC4**: Given a record type and an id, When `netsuite_get_record` is called, Then it returns that record's full field body as NetSuite returns it.
- **AC5**: Given a record type and an id that does not exist, When `netsuite_get_record` is called, Then the connector returns a structured `not_found` error, not a raw 404 passthrough or stack trace.
- **AC6**: Given a record type and a field payload, When `netsuite_create_record` is called, Then it creates the record and returns the created record's internal id and self link.
- **AC7**: Given invalid or missing required field values in the create payload, When `netsuite_create_record` is called, Then the connector surfaces NetSuite's validation rejection as a structured `invalid_argument` error, not a raw stack trace.
- **AC8**: Given a record type, an id, and a partial field payload, When `netsuite_update_record` is called, Then it patches only the given fields (NetSuite `PATCH` semantics) and returns the updated record's id.
- **AC9**: Given a record type and an id, When `netsuite_delete_record` is called **without** an explicit `confirm: true`, Then the connector does **not** call NetSuite's delete endpoint and instead tells the caller confirmation is required.
- **AC10**: Given a record type and an id, When `netsuite_delete_record` is called **with** `confirm: true`, Then the connector calls NetSuite's delete endpoint and returns success.
- **AC11**: Given a SuiteQL `SELECT` statement, When `netsuite_run_suiteql` is called, Then the connector executes it against `/query/v1/suiteql` and returns the resulting rows plus pagination metadata (`offset`, `count`, `has_more`).
- **AC12**: Given a SuiteQL statement NetSuite rejects (a non-`SELECT` statement, or a syntax error), When `netsuite_run_suiteql` is called, Then the connector surfaces NetSuite's rejection as a structured error (the connector does not parse or pre-validate the SQL itself).
- **AC13**: Given a SuiteQL query whose result set exceeds the connector's per-page cap, When `netsuite_run_suiteql` is called, Then the response is truncated to the cap and marked `has_more=true` with the offset needed to fetch the next page.
- **AC14**: Given no credential headers on the request, When any tool is called, Then the connector returns a structured 401 naming the required headers, and no call reaches NetSuite's API.
- **AC15**: Given an invalid, expired, or revoked credential set, When any tool is called, Then the connector surfaces NetSuite's 401/403 as a structured `unauthorized` error.
- **AC16**: Given NetSuite returns a governance-limit / concurrency-limit rejection, When any tool is called, Then the connector surfaces it as a structured `rate_limited` error (`retryable=true`).
- **AC17 (multi-tenant isolation)**: Given two different credential sets used in two concurrent requests (two different NetSuite accounts), When each request is handled, Then each one only ever sees/affects the NetSuite account tied to its own header set — the server holds no cross-request cache or shared state that could leak one account's data into another's response.

### Open questions

- **Q1 (not blocking, assumption recorded)**: Does "every action logged" mean "the connector keeps its own server-side access log" (method/tool/status/duration, no field values or credentials — the logging requirement every MCP in this org already keeps, SOP §6) or "surface NetSuite's own System Notes / audit-trail feature as a tool"? NetSuite does have a System Notes feature (per-record change history) but it requires the "Set Up Audit Trail" feature to be enabled per account and is not guaranteed on. Assumed the former (server-side access logging only) since that is what "encrypted credentials + logged actions" means for every other connector in this org (same assumption recorded on Neon's Q1, Supabase's Q1); if the ticket meant exposing NetSuite's own audit trail as a tool, that is additive once a specific need is named.
- **Q2 (not blocking, assumption recorded)**: Full CRUD (including delete) was included because the ticket's own wording ("live access... with credentials encrypted and every action logged") does not restrict to read-only, and an ERP connector that can only read under-delivers on "live access" relative to what the other connectors in this batch provide for their own domains (e.g. Supabase/Neon branch and secret writes). If the actual appetite is read-only v1, `netsuite_create_record`/`netsuite_update_record`/`netsuite_delete_record` can be dropped without touching the rest of the design — see Decisions made by DEV01, item 3.
- **Q3 (not blocking, assumption recorded)**: The generic account-id → subdomain transform (lowercase, `_` → `-`) is stated in NetSuite's REST Web Services documentation pattern but was not re-verified against a live account this pass (no test account is available in this pipeline's environment, consistent with SOP: not a blocker). The dev leg should confirm this transform against whatever real/sandbox account id is used for manual end-to-end testing before go-live.

## Tech design

### Conclusion

Build `netsuite-mcp` from scratch (main line A) against NetSuite's public SuiteTalk REST Web Services (`https://{account-id}.suitetalk.api.netsuite.com/services/rest/`, Token-Based Authentication / OAuth 1.0a request signing, no login/paywall beyond holding a NetSuite account — confirmed in this pass against Oracle's own REST Web Services API Guide). Follow the `hudu-mcp` / `neon-mcp` / `supabase-mcp` repo shape (same org, same stack) for module layout, per-request credential middleware, structured error envelope, and response-size capping; the one NetSuite-specific wrinkle is that the credential middleware carries **five** header values and every outbound call must be OAuth-1.0a-signed (HMAC-SHA256) rather than a single static `Authorization: Bearer <token>` header.

### Where the current implementation lives

Nowhere yet — `netsuite-mcp@main` (7dfdc56) is a two-line README with no source tree. There is no prior NetSuite connector in `MSPbotsAIFramework` to extend.

### Option analysis

- **Build from SuiteTalk REST Web Services directly (chosen)**: public (to any NetSuite account holder), documented resource model (record CRUD + SuiteQL + metadata catalog), matches every other first-party connector in this org (HTTP wrapper over a vendor REST API, credentials from request headers). No sign-up gate, no partner/paid tier blocking any of the resources this design uses — NetSuite's REST Web Services feature only needs to be enabled in the account's own Setup menu, which is a customer-side one-time toggle, not a vendor-side gate.
- **SuiteTalk SOAP Web Services (the older NetSuite integration API)** — rejected: REST is NetSuite's current, actively documented integration surface; SOAP requires WSDL-generated client code and a materially heavier implementation for no capability this design needs that REST lacks.
- **One tool per record type (e.g. `netsuite_create_customer`, `netsuite_create_vendor`, ...)** — rejected, see Decisions made by DEV01, item 1: NetSuite's record catalog is large and account-customizable; a generic `recordType` parameter is the only approach that scales and stays under the SOP's ≤20-tool guidance.
- **Expose SuiteAnalytics Workbook / saved searches instead of SuiteQL** — rejected: saved searches are account-configuration objects with their own separate permission model and are not part of the REST record/query surface; SuiteQL is the documented, REST-native query mechanism and needs no pre-existing saved-search setup in the target account.

### Decisions made by DEV01

No one was available to ask, so these choices were made directly and are flagged here for review:

- **Generic `recordType` parameter instead of one tool per record type** — why: NetSuite ships hundreds of standard record types and accounts can add custom ones on top; a tool per type would blow past the SOP's ≤20-tool guidance (§2.1) and most tools would sit unused on any given account. Alternative not chosen: hardcode tools for the handful of "obvious" ERP records (customer, vendor, salesOrder, invoice) — rejected because it still misses whatever records a given account actually uses, and the generic approach costs nothing extra once `netsuite_get_record_schema` exists for discovery.
- **SuiteQL as the only search/filter mechanism, not NetSuite's record-list query params** — why: the plain `GET /record/v1/{recordType}` list endpoint only paginates ids, it has no `$filter`-style query support; SuiteQL is NetSuite's own documented way to filter/join/aggregate over REST. Alternative not chosen: try to reverse-engineer undocumented list-endpoint filter params — rejected, unsupported and unstable surface.
- **Full CRUD (including delete) rather than read-only v1** — why: the ticket's own wording ("live access... every action logged") implies acting on the account, not just reading it, and every other connector in this recent batch (Supabase, Neon) ships comparable write/destructive capability for their own domains. Alternative not chosen: ship read-only and defer writes to a follow-up ticket — recorded as Open Question Q2 in case the actual appetite is narrower; dropping the three write tools later does not require touching the read tools.
- **Five separate credential headers, no combined "connection string"** — why: NetSuite Token-Based Authentication is fundamentally five independent values (account id + consumer key/secret + token id/secret) used to build an OAuth 1.0a signature, not a single bearer value; packing them into one header would violate the SOP's "one credential field per Header" rule (§3.1) and make the signing code harder to test. No base-URL override header is offered (unlike some self-hostable vendors) because NetSuite is SaaS-only and the base URL is fully determined by the account id.
- **Record bodies passed through close to NetSuite's native JSON shape, not mapped to a simplified internal schema** — why: NetSuite field sets vary per record type and per account (custom fields), so any fixed internal schema would silently drop or mishandle fields the agent actually needs; `netsuite_get_record_schema` is the discovery mechanism instead of this connector guessing a canonical shape.

To change any of these, say so in a comment and move the ticket back to `5b - ready for groom`.

### Data & API contract

**Transport**: Streamable HTTP, stateless, one container serving every tenant (SOP's three rules: credentials from headers only, per-request isolation, no server-side state).

**Credential headers** (five, all required — NetSuite Token-Based Authentication has no single-token shorthand):

| Header | Required | Meaning | How to get it |
|---|---|---|---|
| `X-Netsuite-Account-Id` | Yes | NetSuite account id (e.g. `1234567` or `1234567_SB1` for a sandbox); used both to build the account-specific base URL and as the OAuth `realm` | NetSuite UI footer, or `Setup > Company > Company Information` |
| `X-Netsuite-Consumer-Key` | Yes | Integration record's consumer key | `Setup > Integration > Manage Integrations > New` |
| `X-Netsuite-Consumer-Secret` | Yes | Integration record's consumer secret (shown once at creation) | Same integration record |
| `X-Netsuite-Token-Id` | Yes | Access token id, scoped to one role | `Setup > Users/Roles > Access Tokens > New` |
| `X-Netsuite-Token-Secret` | Yes | Access token secret (shown once at creation) | Same access token record |

Missing any of the five → 401 listing every missing header name (SOP §3.2). All five are read fresh per request into a `ContextVar`-scoped credentials object and used only to sign that request's outbound call; none are cached, logged, or kept past the request (SOP §3.3/§3.4/§6).

**Record CRUD** (`src/netsuite_mcp/tools/records.py`):

| Tool | Method → NetSuite endpoint | Notes |
|---|---|---|
| `netsuite_list_records` | `GET /record/v1/{recordType}?limit=&offset=` | Returns ids/links only (NetSuite does not filter here — use `netsuite_run_suiteql` to search); `limit` default 50, hard cap 200 (SOP §2.5); response carries `has_more`. |
| `netsuite_get_record` | `GET /record/v1/{recordType}/{id}` | Full field body, passed through close to NetSuite's own JSON shape (see Decisions made by DEV01, item 5) with oversized/irrelevant internal links trimmed per SOP §2.5. |
| `netsuite_create_record` | `POST /record/v1/{recordType}` | Body is the caller-supplied field map; returns the new record's internal id + self link (from the `Location` response header NetSuite returns on create). |
| `netsuite_update_record` | `PATCH /record/v1/{recordType}/{id}` | Partial update — only passed fields are changed, matching PATCH semantics (not `PUT`, which NetSuite treats as full replace). |
| `netsuite_delete_record` | `DELETE /record/v1/{recordType}/{id}` | Requires `confirm: true` in the tool arguments (AC9/AC10); annotated `destructiveHint=True`. Deleting an id that no longer exists is **not assumed idempotent** — NetSuite's documented behavior for delete-of-missing-id was not independently re-verified this pass; the dev leg should confirm the actual response and map it explicitly rather than guessing "success". |

**Metadata** (`src/netsuite_mcp/tools/metadata.py`):

| Tool | Method → NetSuite endpoint | Notes |
|---|---|---|
| `netsuite_list_record_types` | `GET /record/v1/metadata-catalog` | Returns the catalog entries (record type names + links); account-specific (includes any custom records). |
| `netsuite_get_record_schema` | `GET /record/v1/metadata-catalog/{recordType}` with `Accept: application/schema+json` | Returns the JSON Schema for that record type's fields (name/type/required), used by the caller to build valid create/update payloads without guessing. |

**Query** (`src/netsuite_mcp/tools/query.py`):

| Tool | Method → NetSuite endpoint | Notes |
|---|---|---|
| `netsuite_run_suiteql` | `POST /query/v1/suiteql` header `Prefer: transient`, body `{"q": ..., "params": [...]}` | `q` must be a single `SELECT` statement (NetSuite itself rejects anything else — AC12); optional `params` for `?`-style bound parameters (prefer these over string-interpolating caller input into `q`, to keep SQL-injection risk on NetSuite's own parameterization rather than this connector's string handling); `limit`/`offset` query params, default `limit` 50 / hard cap 200 (SOP §2.5) even though NetSuite itself allows up to 100,000 total results per query. |

**Error mapping** (SOP §4.2 fixed vocabulary; NetSuite's REST error body carries `o:errorDetails: [{detail, o:errorCode, o:errorPath}]`, surfaced in the envelope's `message`):

| NetSuite HTTP status | Mapped `code` | `retryable` |
|---|---|---|
| 400 / 422 (validation, bad SuiteQL) | `invalid_argument` | false |
| 401 / 403 | `unauthorized` | false |
| 404 | `not_found` | false |
| 429 / governance-limit rejection | `rate_limited` | true |
| 5xx / timeout / connection error | `upstream_error` | true |

### Key flow / sequence

Discover-then-act (typical agent flow for an unfamiliar record type):

```
1. netsuite_list_record_types        → confirm the type name exists in this account
2. netsuite_get_record_schema        → learn required/optional fields before writing
3. netsuite_run_suiteql              → find candidate records (search/filter/join)
4. netsuite_get_record               → read one record's full detail
5. netsuite_update_record            → change specific fields
   (or netsuite_create_record for a new record, netsuite_delete_record with confirm:true to remove one)
```

Create flow:
```
1. netsuite_get_record_schema(recordType) → required fields
2. netsuite_create_record(recordType, fields)
3. netsuite_get_record(recordType, new id) → confirm what was actually stored (NetSuite may default/derive some fields)
```

### Non-functional

- **Idempotency**: `netsuite_create_record` is never idempotent (NetSuite assigns a new internal id per call). `netsuite_update_record`/`netsuite_get_record` are naturally idempotent (same id, same effect). `netsuite_delete_record`'s behavior on an already-deleted id is **not assumed** — see the note in Data & API contract; must be confirmed, not guessed, before claiming idempotency in the README.
- **Concurrency/perf**: one `httpx.AsyncClient` per request-scoped client factory (no shared client holding one tenant's signed headers across requests); connect/read timeouts and bounded retries with backoff on 429/5xx per SOP §5, total call time < 120s.
- **Security**: all five credential values live only in the request-scoped `ContextVar`, never logged, never cached, never written to disk; the OAuth signature (nonce + timestamp + HMAC-SHA256) is computed fresh per outbound call — no signature or derived value is reused across requests. Structured logs record tool name, record type, NetSuite HTTP status, duration, and mapped error `code` — never field values or credentials (SOP §6).
- **Multi-tenant isolation**: same `contextvars` pattern as `neon-mcp`/`supabase-mcp` (AC17); no module-level singleton holds a client, token, or signed header across requests.
- **Observability**: see Security above — logging is intentionally conservative given NetSuite records routinely carry financial/PII data (customer addresses, invoice amounts).

### Rollout & rollback

New repo, no existing tenant is connected yet — there is no "live" behavior to regress. First deploy is a new-vendor registration (`mcppub register`) against INT per the standard MCP release flow (`mcp-track.md` §4.8); rollback is simply not registering, or redeploying the prior commit, since no tenant traffic depends on this connector yet.

### Risks & dependencies

- **OAuth 1.0a signing correctness**: getting nonce/timestamp/HMAC-SHA256/realm wrong fails silently as a generic 401 from NetSuite, which this connector will (correctly, per the error-mapping table) report as `unauthorized` — indistinguishable from a genuinely bad credential from the caller's point of view. Mitigate with a dedicated unit test asserting the signed header's structure, and a manual end-to-end check against a real account before go-live.
- **No NetSuite test account in this pipeline's environment** — manual end-to-end cases (AC1–AC13 against real data) are deferred, listed in `.ac.json` as `type: manual`, `result: untested`, per SOP ("no test account is not a blocker").
- **Account-specific schema**: every NetSuite account can add custom record types and custom fields on standard records; `netsuite_get_record_schema`'s results will differ per tenant by design (this is a feature of the generic approach, not a gap — see Decisions made by DEV01, item 1).
- **Governance/concurrency limits vary by NetSuite license tier** and were not independently re-verified this pass beyond "NetSuite returns a governance-limit rejection, map it to `rate_limited`" (AC16); exact thresholds are account-plan-specific and not something this connector can or should hardcode.
- No dependency on another in-flight ticket; no gateway change required.
